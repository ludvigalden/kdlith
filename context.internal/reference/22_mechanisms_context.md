# In-scope mechanisms: context

Declared by `pkg/kdl/schemas/dialect/context.kdl`.

| Mechanism                              | What the dialect declares                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Draft         |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| Engine-managed, schema-defined context | The engine manages context but never hardcodes what a context-producing node means; names like `package` or `defaults` gain meaning only through a schema definition                                                                                                                                                                                                                                                                                                                                                                                                                                                               | R1 §4         |
| Typed slots                            | `context { slot NAME TYPE }` with an optional namespace and description; values set into a slot are validated against its type                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | R2 §11        |
| Effect targets                         | `effects target=following` and `effects target=children`; a node affecting both declares two groups                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | R1 §4, R2 §11 |
| Generic effects                        | `set` (from a bound field or a literal value, exactly one), `remove` (the slot becomes unset, not null), `clear` (every slot in a namespace)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | R1 §4         |
| Replacing effect groups                | An effect group may declare `replace=#true`: its set effects replace the held value of the slots they name instead of failing the duplicate-set check (`KDLITH-CTX006`), including the sets a handler in the group splices in; slots the group does not name are untouched, which is what distinguishes it from clear-then-set. A set on an undeclared slot still fails closed — a declarative one as an undeclared reference at compile, a handler's at its effect point (`KDLITH-CTX005`)                                                                                                                                        | R1 §4         |
| Registered handlers                    | `handler NAME` names domain computation implemented by the processor that installs it; a schema naming a handler that is not installed fails clearly. A handler's effects are checked when it runs: one that sets or removes a slot, or clears a namespace, the definition does not declare is rejected at the effect point (`KDLITH-CTX005`) — a run-time fault of the installed handler, distinct from the malformed-construct code a definition fault carries                                                                                                                                                                   | R1 §4         |
| Context-bound fields and policies      | A field may read a slot (`context=` shorthand or a `context` source) under policy `fallback` (supplies the field only when no explicit value is present) or `fixed` (an explicit value must agree)                                                                                                                                                                                                                                                                                                                                                                                                                                 | R1 §4, R2 §10 |
| Execution timing                       | A node is bound against its incoming context, then its effects are computed. Children effects apply on entering the children and must be computable from the node's header; one that depends on a child field is rejected as incompatible with streaming. Following effects apply only after the node completes successfully. Leaving a boundary restores the caller's context. A late effect never changes nodes already bound                                                                                                                                                                                                    | R1 §4, R2 §11 |
| Source context                         | A `source-context` block declares fields derived from source metadata, with sources naming registered source-metadata providers (an unregistered source fails closed). The block declares its mode — `initial`, `fallback`, or `fixed` — explicitly; there is no default, so an undeclared mode is a missing required property (`KDLITH-BND004`), never a silent fallback. Values apply before the document's first semantic node, and every derived value records its origin in provenance                                                                                                                                        | R1 §5, R2 §11 |
| Accumulating context                   | A slot may declare an accumulation policy: `append` for list-typed slots (concatenates in effect order) and `merge` for map-typed slots (key-wise). `merge` declares how a key contributed twice is treated: `duplicates=reject`, the default, rejects it as a duplicate key (`KDLITH-BND006`); `duplicates=last-wins` replaces the held entry's value and keeps the key's first position. `remove` still unsets and `clear` still clears; accumulation is a third policy, not a replacement for either                                                                                                                            | R1 §4         |
| Slot duplicate policies                | A slot that does not accumulate declares how a second value reaching it is treated: `duplicates=reject` (fail-closed default, `KDLITH-CTX006`), `duplicates=reject-different` (a byte-equal repeat is a no-op success that keeps the held value; a differing one is rejected exactly as reject rejects it), `duplicates=last-wins`, or `duplicates=layered` ordering values by declared layer. The held value is the slot's incoming one, inherited by a children scope, projected into an import, or set earlier in the scope; under reject an equal value is still a second value, and reject-different admits only an equal one | R1 §4, R3 §9  |
| Layered slots                          | A layered slot lists its layers highest precedence first (`layers override base`), and every `set` on it names one (`set NAME field=F layer=L`). A higher layer's value replaces a lower one's, a lower layer's leaves the held value in place, and a second value in one layer, or meeting a held value without a layer, is rejected (`KDLITH-CTX006`), so the result does not depend on effect order. A layer on another slot's set, a layered set with none, or `layers` without `layered` is malformed                                                                                                                         | R3 §9         |
| Context snapshots                      | The engine persists context as shared immutable snapshots or checkpoint-plus-delta chains and records, per indexed record, its identity and type, source digest and span, schema fingerprint, context snapshot ID, invocation ID, and validation status. On-demand resolution restores the snapshot and binds the recorded span instead of replaying every preceding control. A restore whose schema fingerprint or invocation lineage does not match is rejected (`KDLITH-CTX004`); forward context makes entering an arbitrary node without a prior scan impossible by construction, not policy                                  | R1 §7         |
