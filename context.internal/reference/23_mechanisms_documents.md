| Source imports                   | `import PATH` with role `source-import`, optionally `as=NAME`. The path is a location: relative to the importing document, from its source's root (`/`), or from a named source's root (`$name/`), never leaving that source and never computed beyond the patterns the governing locations rule admits. The imported document receives only the `project` list of the caller's slots, and its context mutations never return to the caller. Cycles are diagnosed from the active invocation stack; import order is the order of the import nodes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | R1 §5, R2 §11, R3 §10 |
| Repeated imports                 | `repeated=reject` (the fallback), `coalesce` (equal context reuses the first invocation), or `instantiate` (each import is a separate invocation)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | R1 §5                 |
| Document profiles                | `profile NAME { roots { allow TYPE ... } }` name selections of roots and nodes; a node declaration may carry `profile=NAME` so one node name binds differently per profile. Dispatch is by profile, parent binding, node name, and explicit discriminators — never by trying profiles until one accepts. A profile may carry `extends=NAME` (child-over-parent composition of roots, match rules, and locations; `default` never inherited), `default=#true` (one per schema, `KDLITH-SCH013`), and `match` rules — `path-suffix`, `path-prefix`, `file-name` comparing the document's root-relative source path, split on `/` and `\`, exactly and case-sensitively. Selection resolves once per entry document before any node binds, in one total order: an explicitly named profile; else, under a listed profile set, the listed profiles whose rules match, else the listed default, else `KDLITH-SCH011` (a set never falls through to inference or the schema default); else the first declared match rule the path satisfies; else the schema's default; else `KDLITH-SCH011`. An `extends` cycle is `KDLITH-SCH012`; an undeclared name anywhere is `KDLITH-SCH011` or `KDLITH-SCH006` on a declaration                                                                                                                                                                                                                                                                                                                                                                                                                                                           | R3 §3                 |
| Descendant rules                 | Structural rules may range over descendants rather than immediate children: a node declaration bounds occurrences of a named node anywhere in its subtree, checked when the declaring scope completes. Descendant rules stop at the subtree of their declaring node and never cross an import boundary. A violation reports `KDLITH-BND002` like any occurrence rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | R1 §3                 |
| Ordered sequences                | A node declaration may require its immediate children to match an ordered sequence with alternatives, compiled into the same per-scope state machine; a child arriving where the compiled sequence does not admit it is rejected (`KDLITH-BND002`). Repetition stays with `min-occurs` and `max-occurs` on a step; there are no unbounded-repetition groups at this version                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | R1 §3                 |
| Locations rules                  | `locations { patterns star=… doublestar=… braces=… }` on the schema root or a profile, with `allow-empty=#true`, admits pattern locations: the root's rule governs the schema's own imports and data no profile rule governs, a profile's governs the data it reads, and without a rule only literal locations import. Expansion lists the location's source; environment-variable interpolation is admitted by no rule (`KDLITH-LOC004`). Matches are ordered by portable path bytes; a pattern matching zero documents does not resolve (`KDLITH-LOC001`) unless the rule allows an empty match; and the resulting inventory is itself a dependency                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | R3 §10                |
| Import namespaces                | An import may carry `as=NAME`: the import request preserves both the source and its namespace, and a resolved request records the shown paths of the targets it loaded. A document imported under a namespace resolves its own declarations unqualified; every other document reaches them only through the namespace. A namespace must be unique in its document (`KDLITH-BND006`), and a gated reference that cannot resolve is `KDLITH-REF001`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | R3 §5                 |
| Symbol catalogs                  | Declarations carry identity: an `identity { domain NAME compose qualified-name FIELD FIELD }` block composes a declaration's qualified symbol from bound fields, and `reference NAME target=TYPE` declarations state a reference's registered syntax codec, lookup domain, and qualification policy (`explicit`, `explicit-or-context`, `imported-or-context`) with declared required qualifiers. A data field whose type names a declared reference type binds a value of that reference: the codec capture whose name matches a declared qualifier becomes that qualifier, the remaining captures become the name segments in declaration order, and the `namespace` slot in effect at the field's position is captured only when the policy admits context. A reference declaration may carry an `open-world system-member=FIELD values="V1 V2 ..."` child (one whitespace-separated value set): a reference of that type resolving to no candidate links external — no diagnostic — when the declaration its outermost identity segment names is indexed and holds a listed value in that member, and the arm is `KDLITH-SCH021` at compile when its target composes no identity or its member or a listed value is statically wrong against the type the outermost field's declared qualifier names. Identity construction, reference binding, lookup policy, and linking are separate stages held by the compiled symbol catalog. Two declarations composing the same qualified identity in one domain are `KDLITH-REF002`; a reference resolving to no candidate is `KDLITH-REF001`, to several `KDLITH-REF003`, to one failing a required qualifier `KDLITH-REF004` | R3 §5, R3 §11         |
| Contribution resolution          | Contributions stay preserved records — target, value, layer, application scope, source origin — and resolution across layers is performed by a configuration resolver the processor registers, never by lexical context replacement and never by the engine itself. The schema declares the policy the resolver applies as descriptors; a schema naming a resolver that is not installed fails closed (`KDLITH-DLC006`). kdlith ships one resolver, registered as `layered`, admitted alike by every verb that loads a schema and installed statically by a generated crate through `reader_with_contribution_resolver`, whose typed reading yields the same resolution items, while the plain `reader` leaves contributions as records. Per (target, scope) partition, in sorted order with the scope-less partition first: `layers` orders precedence highest first; same-rank records are duplicates, which `reject` refuses and `last-wins` settles by document order; `replace` selects the highest-ranked value and `union` merges value maps deeply (per-field merge below); `missing reject` refuses a contribution holding a reference naming a target no record resolves within the referencing record's own scope. Each refusal fails the reading as `KDLITH-DLC010`. Each settled target follows as one `resolution` item per scope; resolved output is derived from bound records, so it adds nothing to the cache identity                                                                                                                                                                                                                                    | R3 §9                 |
| Computed defaults                | A default may be computed: bound through a union of literal and computed alternatives discriminated by property, it is a descriptor carrying its dependencies as typed references. The processor never computes it. A required field whose only fallback is computed is missing-required (`KDLITH-BND004`) when no value binds and no registered value resolver supplies one; an optional one stays absent                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | R3 §8                 |
| Secret providers                 | A secret provider is descriptor data: an identifier, an optional TTL, and a command as a list of strings preserving argument boundaries. It is never executed, never reinterpreted as a shell command string, and the CLI never executes provider commands to validate or export declarations. Provider references and resolved secret values stay separate fields, and every serialization and diagnostic surface applies the explicit output policy                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | R3 §8                 |
| This dialect's own document rule | A dialect definition has exactly one `dialect` root; a schema definition has exactly one `schema` root                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | F §1                  |
| Document rules are records       | `document` has role `record`: a document rule is a validated statement about the documents a definition reads, with no identity of its own. It occurs at most once per root                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | R3 §2                 |
